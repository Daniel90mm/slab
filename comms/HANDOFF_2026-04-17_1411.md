## Open threads

### Core architectural recommendation

Do **not** make raw `.ipynb` editing the primary LLM interface for Culmen.

Preferred model:

- notebook is the user-facing authoring format
- Culmen still thinks in markdown for scaffold/review tasks
- a deterministic adapter sits between them

This avoids asking the LLM to rewrite notebook JSON directly while still letting the user work in notebooks.

### Recommended data flow

#### Scaffold generation

`Culmen scaffold markdown -> deterministic parser -> notebook cells -> .ipynb`

#### Review

`user-edited .ipynb -> deterministic flattening of markdown cells -> review markdown -> LLM review -> feedback .md`

This preserves the strongest current invariant: the review model still sees one linear markdown document.

## Technical decisions

### 1. Notebook is the authoring artifact, markdown is the review projection

Decision:

- Treat `.ipynb` as the thing the user edits.
- Treat flattened markdown as a derived artifact used for Culmen review and possibly other LLM tasks.

Why:

- keeps the notebook UX available
- keeps Culmen's LLM prompts mostly unchanged
- avoids direct freeform edits to notebook JSON

Tradeoff:

- now there are two representations
- requires a reliable deterministic adapter

### 2. Use markdown cells only for note content

Decision:

- Only flatten notebook **markdown** cells into review markdown by default.
- Ignore code cells and outputs during review unless explicitly opted in later.

Why:

- matches current Culmen notes model
- keeps review content focused on student-written notes
- avoids polluting review prompts with code/output noise

Tradeoff:

- if the user writes meaningful content in code cells or output areas, it will be omitted from review
- could be extended later with explicit inclusion rules

### 3. Preserve structure using cell metadata

Decision:

When generating notebooks from scaffold markdown, create paired markdown cells with stable metadata, e.g.

- `culmenRole: "prompt"` or `culmenRole: "answer"`
- `culmenSectionId: "<stable-id>"`
- `culmenSectionTitle: "<heading text>"`
- `culmenGenerated: true|false`

Why:

- makes round-tripping more stable
- lets the extension or Culmen distinguish scaffold text from student answers
- gives future edit operations a stable anchor

Tradeoff:

- some metadata complexity in the notebook file
- still much safer than editing notebook JSON semantically with no anchors

### 4. Generate scaffold notebooks as prompt/answer cell pairs

Decision:

Convert scaffold markdown sections into notebook cells like:

- top title/introduction cell
- per section:
  - prompt cell containing the question/instructions
  - answer cell containing `_Write your notes here._` or existing answer content

Why:

- maps naturally to the current Culmen learning loop
- visually separates scaffold and user answer space
- makes flattening predictable

Tradeoff:

- the notebook will no longer be a single continuous markdown block
- some LaTeX semantics that depend on global continuity will still need a later virtual-document layer

### 5. Flatten review markdown in a deterministic, linear order

Decision:

Flatten notebook cells into one review markdown document using notebook order.

Suggested output shape:

- notebook title/frontmatter if present
- for each section:
  - prompt heading / prompt text
  - answer content
  - separator `---`

Why:

- matches the current scaffold-and-answer review structure
- keeps the LLM prompt easy to reason about
- stable ordering reduces review drift

Tradeoff:

- cell-local rendering quirks disappear in the flattened view
- notebook-only constructs such as `attachment:` need translation

### 6. Convert notebook attachments to file-based markdown references before review

Decision:

For review markdown, rewrite notebook-local image references like:

`![image.png](attachment:image.png)`

into deterministic file-based references, ideally under a concept-local assets path, e.g.

`![](./assets/image.png)`

Why:

- Culmen already understands file-based markdown assets much better than notebook attachments
- makes review markdown portable

Tradeoff:

- requires materializing attachment blobs to disk if they only live inside the notebook
- introduces an asset sync concern

### 7. Do not try to preserve notebook outputs in review markdown

Decision:

- Exclude outputs entirely from the markdown review projection in the first version.

Why:

- outputs are noisy
- they increase token cost heavily
- they are not part of the user's explanatory note-writing loop

Tradeoff:

- if a student relies on output as part of their explanation, the review model will not see it

### 8. Keep feedback files as markdown

Decision:

- Continue writing feedback as `.md` in the `feedback/` folder.

Why:

- this already works
- feedback is naturally linear prose
- avoids introducing another notebook conversion path unless there is a clear user benefit

Tradeoff:

- notebook authoring and feedback viewing remain slightly asymmetric
- probably acceptable and maybe desirable

## Proposed flattening algorithm: `.ipynb -> review markdown`

### Inputs

- notebook JSON
- notebook path
- optional adapter config

### Steps

1. Parse notebook JSON with a real notebook parser, not regex/string hacks.
2. Iterate cells in order.
3. Select markdown cells only.
4. For each markdown cell:
   - capture `source`
   - inspect `culmenRole`, `culmenSectionId`, `culmenSectionTitle` if present
   - normalize line endings
   - resolve notebook attachments
5. Build one linear markdown document:
   - preserve headings/math/tables exactly where possible
   - insert stable separators between logical sections
6. Emit mapping info:
   - flattened range -> cell index/id
   - cell index/id -> flattened range

### Important rule

Flattening should be as **lossless** as possible for markdown semantics, but it does **not** need to preserve notebook JSON formatting or source trivia.

## Proposed generation algorithm: `scaffold markdown -> .ipynb`

### Inputs

- scaffold markdown produced by Culmen
- target notebook path

### Steps

1. Parse markdown structurally:
   - title
   - top-level and second-level headings
   - `_Write your notes here._`
   - separators `---`
2. Convert each scaffolded learning block into notebook cells:
   - prompt/instruction cell
   - answer cell
3. Add stable metadata to each generated cell:
   - role
   - section id
   - section title
4. Initialize answer cells with placeholder text or blank content.
5. Write a valid `.ipynb` with minimal metadata and no outputs.

### Important rule

The generator should produce **clean notebooks with empty outputs** and only the minimum metadata needed for stable tracking.

## Tradeoffs summary

### Option A: direct LLM read/write on raw `.ipynb`

Pros:

- fewer conversion layers
- notebook is the only source of truth

Cons:

- higher token overhead
- more fragile edits
- risk of notebook corruption
- harder insertion semantics
- harder asset handling

Verdict:

- possible, but not preferred for Culmen's scaffold/review loop

### Option B: notebook authoring + deterministic markdown projection

Pros:

- preserves current Culmen mental model
- keeps review prompts simple
- safer than freeform notebook rewriting
- easier to test

Cons:

- adapter complexity
- must maintain cell/source mapping
- notebook-only features need explicit conversion

Verdict:

- best current recommendation

## What this design does not solve yet

- global equation numbering across cells
- labels/refs across cells
- BibTeX integration
- Overleaf-like continuous document semantics
- custom rendering of multi-column figure layouts
- Slab-like source coloring/decoration quality inside notebook editors

Those require a later **virtual document engine** on top of the adapter.

## Do not

- Do not let the LLM freely rewrite the full `.ipynb` as plain text.
- Do not include code outputs in first-pass review markdown.
- Do not make feedback notebooks yet; keep feedback as markdown until there is a clear need.
- Do not couple the first adapter implementation to preview/rendering work.
