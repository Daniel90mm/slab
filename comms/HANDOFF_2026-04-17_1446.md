- flattened markdown is the review projection
- Culmen still reviews markdown
- feedback stays markdown

The change is **how** attachment cleanup happens, not the overall notebook/markdown architecture.

### Implementation language is now explicit

Decision:

- Phase 2 stays in **plain JavaScript**
- use `type: module` / CommonJS consistently with the existing repo conventions
- use JSDoc for structure where needed
- do not add `.ts` files, `tsconfig.json`, or a build step in this phase

Why:

- repo is already JS-only
- Phase 2.0 is mostly raw JSON transformation and file IO

Tradeoff:

- less static safety than TS
- acceptable for Phase 2; if TS is later desired, do it as an explicit conversion pass

## Technical decisions

### 1. Raw-file extractor over hook-first attachment mutation

Decision:

- Attachment extraction must operate on raw `.ipynb` bytes from disk first.

Why:

- notebook markdown attachments live in serializer-owned notebook JSON
- the VS Code in-memory notebook API does not guarantee direct access to those raw attachment blobs for native Jupyter notebooks
- raw-file transformation is the only guaranteed-correct path

Tradeoff:

- more manual than a transparent save hook
- but far more reliable

### 2. Manual command first, hook deferred behind a spike

Decision:

- Phase 2.0 ships a **manual** extraction command first
- any save-hook automation is **deferred**
- a short spike should test what `NotebookDocument`, cell metadata, and related VS Code APIs surface for a pasted-image markdown cell

Why:

- if attachments are not visible through the runtime notebook API, a save-hook approach is not viable for native `.ipynb`
- this should be proven quickly, not assumed

Tradeoff:

- first user experience is more manual
- but the implementation path is honest and testable

### 3. Extraction must be atomic

Decision:

- Extraction is all-or-nothing:
  - parse notebook JSON
  - extract/write assets
  - rewrite notebook JSON
  - atomically replace the notebook file

If any step fails, leave the notebook unchanged.

Why:

- avoids broken `./assets/...` references
- avoids notebooks that still contain inline attachments but point elsewhere
- avoids partially migrated states

Tradeoff:

- slightly more code for temp-file handling
- worth it

### 4. Feedback stays `.md`

Decision:

- Feedback files remain markdown under `feedback/`

Why:

- feedback is linear prose, not an interactive notebook workflow
- VS Code's built-in markdown preview already handles GFM tables and KaTeX-style math rendering well enough for this use
- `.ipynb` adds cells, metadata, and overhead without meaningful benefit here

Tradeoff:

- authoring surface and feedback surface are asymmetric
- that is acceptable and likely preferable

### 5. Slab performance is not a Phase 2 design input

Decision:

- Treat Slab rendering/performance as a separate track
- do not let it influence the notebook adapter's storage/pipeline design

Why:

- the adapter should emit standard `.md` and `.ipynb`
- renderer performance is a consumer concern, not a format-contract concern

Tradeoff:

- none for Phase 2

### 6. Semantic roundtrip equality, not byte equality

Decision:

- Roundtrip tests compare normalized markdown semantics, not raw bytes

Normalize at least:

- trailing newlines
- fence formatting
- whitespace-only line differences that do not change markdown meaning

Why:

- parsers/stringifiers often normalize formatting
- byte equality is too brittle

Tradeoff:

- requires a small normalization helper in tests

## Updated Phase 2.0

### Deliverables

- `src/attachments/extract.js`
  - pure function:
  - input: raw `.ipynb` bytes or parsed JSON
  - output: `{ nextJson, assets }`
  - where `assets` is an array of `{ path, bytes }`

- `src/commands/extractAttachments.js`
  - manual command for the active notebook file
  - read notebook from disk
  - run extractor
  - write assets
  - write notebook atomically via temp file + rename

- `tests/smoke/extract-attachments.mjs`
  - golden fixture test with inline attachment(s)

- **Spike**
  - minimal logging experiment against a real pasted-image notebook cell
  - inspect what VS Code exposes on the notebook object and cells
  - result decides whether any hook-based convenience path is pursued later

### Naming rule

- `paste-<YYYYMMDD>-<HHMMSS>.<ext>`
- local time
- preserve extension based on MIME type

### Edge cases

- multiple attachments in one cell
- filename key reuse such as repeated `image.png`
- non-PNG image MIME types
- untitled notebooks with no sensible `./assets/` destination

## Deferred hook policy

Do **not** assume a notebook save hook is available for attachment extraction.

Instead:

1. run the spike
2. inspect the actual exposed data
3. only if attachments are reachable and mutation semantics are safe, consider a convenience hook later

If not, commit to:

- raw-file extractor
- manual command
- possibly a later file-watcher/convenience layer

but **not** a magical save hook that depends on hidden serializer behavior

## Adapter design after Phase 2.0

Once attachment cleanup is proven, proceed to the adapter:

- `markdown scaffold -> notebook`
- `notebook -> review markdown`

Still using these rules:

- markdown cells flatten to markdown
- code cells flatten to fenced code blocks with language tags
- outputs excluded in v1
- images always normalized to `./assets/...`
- no MyST, no percent format, no custom directives

## Do not

- Do not let the LLM rewrite raw `.ipynb` JSON.
- Do not ship the adapter before the attachment extractor works on real notebooks.
- Do not use a non-atomic background write strategy for assets.
- Do not author feedback as `.ipynb`.
- Do not bundle Slab performance work into Phase 2.
- Do not introduce TypeScript opportunistically in this phase.
